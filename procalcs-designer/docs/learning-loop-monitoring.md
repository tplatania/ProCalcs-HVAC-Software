# Learning-loop monitoring (Day-25)

Answers Gerald's four operational questions: is Richard's team using
it, are they using it right, is the app learning from them, and when
do we have enough signal to judge the mechanisms.

## The machinery

| Piece | Where | What it does |
|---|---|---|
| `usage_events` table | procalcs-bom Postgres (`models/usage_event.py`, migration `a7e2c9d4b1f6`) | One row per meaningful interaction: `bom_generated`, `chat_message`, `attachment_uploaded`, `override_saved` (+ reserved: `proposal_applied`, `question_answered`) |
| Provenance tagging | derived server-side from the OAuth-forwarded email | Actors in `TEST_ACTOR_EMAILS` (default: Gerald + dev) are stored as `provenance=test` and **excluded from every metric**. Gerald can exercise the full surface — chat, sniping, prices — without polluting the numbers. Add QA accounts via env, no deploy needed. |
| `GET /api/usage/summary` | designer BFF → `/api/v1/usage-events/summary` | Adoption: events by type, per-day timeline, distinct real actors. `?days=N`, `?include_test=1`. |
| `GET /api/usage/impact` | designer BFF → `/api/v1/usage-events/impact` | **Loop closure.** Walks `bom_runs.generated_bom` (every line carries `override_id` audit marks) and counts, per override, how many *later* runs it auto-applied to. Retroactive — works on all 350+ historical runs, no backfill needed. |
| Impact strip | BOM Review Assistant sidebar | "Your team taught this BOM engine N corrections — auto-applied M× across later BOMs", with the top re-applied SKUs. The transparency loop: people keep feeding systems that visibly remember them. |
| `monthly_scoreboard.py` | `scripts/corpus-analysis/` | Re-runs the v6 base scoreboard + computes override coverage over corpus part keys; appends to `scoreboard_history.jsonl`. |

## What counts as a loop closure

A correction entered on BOM A that auto-applies on a *later* BOM B,
generated by a real (non-test, non-anonymous) actor. The run where
the correction was first entered does not count. Runs with no actor
email are excluded by default — historically those are smoke-suite
calls.

## Decision thresholds (agreed 2026-07-18)

- **Mechanism proven**: 10–15 loop closures across ≥3 different plans
  and ≥2 different people. Expected within 4–6 weeks of real usage.
- **Tripwire (new strategy needed)**: ≥50 real inputs accumulated and
  override coverage moved <1 point since the last scoreboard run —
  `monthly_scoreboard.py` exits 2 and says so.
- **Abandonment signal**: rows stuck at "needs price" for weeks, or
  chat proposals consistently ignored (watch `actions_proposed` vs
  `override_saved` in /summary).

## Monthly ritual

```bash
cd scripts/corpus-analysis
python3 monthly_scoreboard.py            # full (~10 min)
python3 monthly_scoreboard.py --skip-base  # overlay only (seconds)
```

Needs `BOM_SERVICE_TOKEN` (Secret Manager) or a staging session
cookie; corpus paths default to the 2026-07-15 full-corpus run.

## Deliberately not built

- No auto-learning from chat free text. A chat statement becomes a
  rule only through the reviewed promotion path (ledger discipline —
  provenance or it didn't happen).
- No per-user surveillance dashboards. Summary aggregates per actor
  for adoption counts; the point is loop health, not activity
  policing.
